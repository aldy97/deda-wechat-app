# 设备端 HTTP 接口文档

版本：1.1，2026-11-10。面向客户后端与设备端对接，与同目录[《MQTT交互协议.md》](MQTT交互协议.md)配套使用。

## 一、对接范围与完整流程

### 1.1 HTTP 与 MQTT 分别负责什么

设备联网后先通过 HTTP 主动上报设备身份，获取三方 LLM 接入所需的 API KEY；设备状态、心跳和常规控制继续走 MQTT。每轮语音对话开始和结束时，再通过 HTTP 通知后端更新本轮智能体实例记录。

| 通道 | 接口或主题                             | 何时调用                            | 后端需要处理的内容                                      |
| ---- | -------------------------------------- | ----------------------------------- | ------------------------------------------------------- |
| HTTP | `POST /client/user/user/loginMac`      | 设备联网后，进入业务前              | 校验设备身份，登记设备，响应头返回三方 LLM API KEY      |
| MQTT | `device/up/{mac}`、`device/down/{mac}` | MQTT 连接建立后持续使用             | 接收状态和心跳，向指定设备下发指令                      |
| HTTP | `POST /client/bot/bot/start`           | 每轮智能体实例创建且 RTC 连接成功后 | 保存设备与本轮百度应用、实例及控制鉴权信息的对应关系    |
| HTTP | `POST /client/bot/bot/stop`            | 每轮对话结束时                      | 按设备 MAC 和实例 ID 标记本轮结束，清理对应控制鉴权信息 |

### 1.2 为什么在原 MQTT 协议之外增加三个 HTTP 接口

此前 MQTT 文档中的设备绑定上报使用公共主题 `loginMac`，本版取消该主题，改为 HTTP `POST /client/user/user/loginMac`。后端无需实现旧 MQTT 绑定流程，设备也无需订阅或发布该公共主题。

多个设备向公共 MQTT 主题上报时，可以通过消息体区分设备；但公共主题本身不带设备 MAC。若还需要向每台设备单独返回 API KEY 和处理结果，就必须额外约定响应主题、设备隔离和请求响应关联规则。HTTP 每次请求都有对应响应，适合完成设备身份校验及密钥返回，因此本次采用 HTTP。

三个 HTTP 接口分别解决三个时间点的问题，不能用一条 MQTT 心跳代替：

| 接口       | 解决的问题                                     | 为什么需要                                                                |
| ---------- | ---------------------------------------------- | ------------------------------------------------------------------------- |
| `loginMac` | 当前是哪台设备上线，它使用什么三方 LLM API KEY | 设备需要拿到 API KEY 后配置三方 LLM 接入；MQTT 心跳不承担密钥返回         |
| `start`    | 这台设备本轮正在使用哪个百度智能体实例         | 同一台设备每轮可能创建不同实例，后端需要知道当前实例及其控制鉴权信息      |
| `stop`     | 这台设备的哪个实例已经结束使用                 | 及时结束本轮登记，避免继续操作已结束的实例；MQTT 仍在线不代表对话仍在进行 |

**后端需要提供三个 HTTP POST 接口，并继续支持原有按 MAC 区分的 MQTT 上下行主题。**

### 1.3 设备执行顺序

1. 设备联网，调用 HTTP `loginMac` 上报 MAC 和校验密码。
2. 后端校验成功，在响应头 `Authorization` 中返回三方 LLM API KEY；设备读取并保存，用于三方 LLM 接入。
3. 设备连接 MQTT，订阅 `device/down/{mac}`，上报初始 `query` 状态，随后每5秒发送心跳。
4. 用户发起对话时，设备负责创建百度智能体实例、配置三方 LLM 接入并连接 RTC。
5. 实例创建且 RTC 连接成功后，设备调用 HTTP `start` 登记本轮实例。后端保存本轮记录，返回 `{"code":200}`。
6. 对话结束时，设备调用 HTTP `stop` 通知本轮结束，并自行断开 RTC、释放云端实例。后端结束对应记录，返回 `{"code":200}`。
7. 下一轮对话重复步骤4至6；只要设备仍在线，MQTT 心跳持续上报。

`start` 是“登记已创建的实例”，不负责创建实例，不返回 RTC token、房间号或 License。`stop` 是“结束登记的通知”，不代替设备释放百度云端实例。HTTP 登记成功、MQTT 在线、RTC 已连接分别代表不同状态。

### 1.4 通用约定

- HTTP 基础地址由客户后端提供，生产环境使用 HTTPS。
- 三个接口均为 POST，请求使用 `Content-Type: application/json; charset=utf-8` 和 UTF-8 编码。
- 设备发送 `Content-Length`，不使用 chunked 请求；请求体最多32768字节。
- MAC 统一为无分隔符的十二位小写十六进制，例如 `aabbccddeeff`；HTTP 与 MQTT 中同一设备使用相同 MAC。
- HTTP 状态码为200且响应体 `code` 为200时，设备才按成功处理。
- `start`、`stop` 的成功响应只需 `{"code":200}`；失败响应统一为 `{"code":错误码,"msg":"错误原因"}`，HTTP 状态与 `code` 一致。

## 二、鉴权与密钥说明

### 2.1 loginMac 响应头 Authorization：三方 LLM API KEY

`loginMac` 校验成功后，后端必须通过 **HTTP 响应头** **`Authorization`** **返回用于三方 LLM 接入的 API KEY**：

```http
Authorization: <三方LLM API KEY>
```

设备读取该响应头，将其值用于三方 LLM 接入配置中的 API KEY。这个值应与后端三方 LLM 服务的鉴权配置匹配；返回一个仅供上线登记使用的随机 token 无法满足该用途。

`start`、`stop` 请求头不携带 `Authorization`。设备将 loginMac 响应头中的值存入全局 API KEY 变量，创建百度实例时填入三方 LLM 配置的 `llm_token`；该值不作为本协议通知接口的鉴权凭据。

密钥有效期、轮换策略由客户后端统一管理，本版不在响应体返回有效期字段。设备不得将该值写入普通日志；密钥失效应按三方 LLM 接入结果处理并重新获取，不以 start/stop 的响应判断 LLM 密钥是否有效。

### 2.2 start 请求体 authorization：百度实例控制鉴权信息

本次固件与本地工具的第一步接入，`authorization` 固定为设备使用预留 AK/SK 计算的**切换角色或音色**签名，对应 `PUT /api/v1/aiagent/instances/operation?switchSceneRole=`。签名的规范化路径为 `/api/v1/aiagent/instances/operation`，规范化查询串包含 `switchSceneRole=`。该签名不能用于创建实例或 `POST /api/v1/aiagent/interrupt` 打断播报；后续如需同时支持不同操作，应分别约定并上传对应签名。本地演示鉴权仅用于三个接口联通，不代表百度已接受鉴权。

`start` 请求体中的小写字段 `authorization` 是设备为本轮百度实例控制准备的鉴权信息。后端保存后，如需调用百度控制接口，将它作为对应请求的 `Authorization` 头使用。

| 名称                        | 来源                             | 用途                                      |
| --------------------------- | -------------------------------- | ----------------------------------------- |
| HTTP 响应头 `Authorization` | 客户后端在 `loginMac` 成功时返回 | 三方 LLM API KEY，仅用于三方 LLM 接入配置 |
| JSON 字段 `authorization`   | 设备在 `start` 中上报            | 百度本轮实例的控制鉴权信息                |
| RTC token                   | 设备创建实例时取得               | 设备连接 RTC                              |

三者用途不同，不能互相替代。设备提供的百度控制鉴权信息必须适用于实际控制请求的方法、路径、云节点及有效期；创建实例使用的签名不能默认适用于其他控制请求。鉴权信息不回显到响应体、不写入普通日志；需要更新时，可按第四节重新登记同一实例。

## 三、设备上线与 API KEY 获取

### 3.1 请求

`POST /client/user/user/loginMac`

设备联网后主动调用，无需预先携带 `Authorization` 请求头。后端以 MAC 识别设备并进行上线登记；设备与用户的绑定关系由后端业务处理，本接口不额外要求用户参数。

| 请求字段 | 类型   | 必填 | 说明                                      |
| -------- | ------ | ---- | ----------------------------------------- |
| mac      | string | 是   | 设备 MAC，规范化后如 `aabbccddeeff`       |
| password | string | 是   | 按下述规则生成的32位小写十六进制 MD5 文本 |

计算密码前，先删除 MAC 中的 `:`、`-` 分隔符，并转为十二位小写十六进制；后端使用同样规则规范化 MAC。

macKey：`1ekyJDsGDn9rC2wXb7tHtfScAcAYP5pR`。

算法：`first = md5_utf8(macKey + normalizedMac).hexdigest()`，`password = md5_ascii(first).hexdigest()`。两层均使用小写十六进制文本，第二层对第一层的32字符文本计算，不是对原始16字节摘要计算。

```json
{
  "mac": "aabbccddeeff",
  "password": "<按上述规则计算的32位小写MD5>"
}
```

### 3.2 成功响应

HTTP 状态码：200。响应头必须包含：

```http
Authorization: <三方LLM API KEY>
```

响应体：

```json
{
  "code": 200,
  "data": {
    "id": "aabbccddeeff",
    "nickname": "设备 ddeeff",
    "lang": "zh"
  },
  "msg": "success"
}
```

| 返回位置    | 字段          | 说明                           |
| ----------- | ------------- | ------------------------------ |
| 响应头      | Authorization | 三方 LLM API KEY，设备必须读取 |
| 响应体 data | id            | 设备标识                       |
| 响应体 data | nickname      | 设备名称                       |
| 响应体 data | lang          | 设备语种，例如 `zh`            |

重复上线按同一 MAC 更新登记，不重复创建设备。后端返回当前可用的 API KEY；设备以最近一次成功响应头中的值为准。上线接口不创建或停止百度实例，每轮实例由 `start`、`stop` 登记。

## 四、智能体连接登记

### 4.1 请求

`POST /client/bot/bot/start`

调用时机：设备已创建本轮百度智能体实例，且 RTC 连接成功后。

请求头：

```http
Content-Type: application/json; charset=utf-8
```

| 请求字段      | 类型   | 必填 | 说明                                                                                   |
| ------------- | ------ | ---- | -------------------------------------------------------------------------------------- |
| mac           | string | 是   | 设备 MAC，与上线设备一致                                                               |
| appid         | string | 是   | 本轮百度应用 ID，最长100 UTF-8字节                                                     |
| instanceid    | string | 是   | 百度 ai\_agent\_instance\_id，正的有符号64位整数，以十进制字符串传输，避免整数精度丢失 |
| authorization | string | 是   | 本轮百度实例控制鉴权信息，ASCII 文本，最多8192字节，无控制字符                         |
| cloud\_node   | string | 否   | `cn`（默认）、`overseas`（海外非欧美）、`euUs`（欧美）                                 |
| lang          | string | 否   | 创建实例时实际语种，默认 `zh`                                                          |

```json
{
  "mac": "aabbccddeeff",
  "appid": "your-baidu-app-id",
  "instanceid": "9223372036854775806",
  "authorization": "<设备准备的百度实例控制鉴权信息>",
  "cloud_node": "cn",
  "lang": "zh"
}
```

### 4.2 成功响应与后端处理

HTTP 状态码：200。响应体：

```json
{ "code": 200 }
```

后端以 `mac` 和 `instanceid` 识别本轮登记，保存应用 ID、云节点、语种和控制鉴权信息。对同一设备、同一实例的重复请求应进行幂等处理，仍返回 `{"code":200}`，允许更新控制鉴权信息；不在响应体增加登记详情。

同一设备上报新实例时，后端将其登记为当前实例，旧实例记录不得继续作为当前实例使用；此操作不自动停止旧云端实例。已结束的实例不得因延迟到达的重复 `start` 被重新激活，冲突时返回409。

本版以设备 MAC 和实例 ID 标识登记。设备应串行发送各轮登记通知，新一轮开始后停止重试上一轮 `start`。该接口不包含独立轮次序号，后端不能仅凭实例 ID 数值大小判断新旧；跨实例乱序处理如需增强，应在后续协议中单独约定。

## 五、智能体退下通知

### 5.1 请求

`POST /client/bot/bot/stop`

调用时机：设备退出本轮对话时。请求头仅需 `Content-Type: application/json; charset=utf-8`，不携带 `Authorization`。

| 请求字段   | 类型   | 必填 | 说明                                                         |
| ---------- | ------ | ---- | ------------------------------------------------------------ |
| mac        | string | 是   | 设备 MAC                                                     |
| instanceid | string | 是   | 要结束的本轮实例 ID，与 `start` 登记一致，以十进制字符串传输 |

```json
{
  "mac": "aabbccddeeff",
  "instanceid": "9223372036854775806"
}
```

### 5.2 成功响应与后端处理

HTTP 状态码：200。响应体：

```json
{ "code": 200 }
```

后端按 `mac` 和 `instanceid` 结束对应记录，清理该记录中的百度控制鉴权信息。重复退下应幂等返回 `{"code":200}`。旧实例的延迟退下通知不得清理同一设备的新实例；未知实例或不匹配的 MAC 返回404。

退下通知失败可重试原请求，保留原 `mac` 和 `instanceid`，不能仅按 MAC 清理当前实例。该响应只确认后端已处理通知，设备仍负责 RTC 断开及云端实例释放。

## 六、错误与重试

### 6.1 错误响应

```json
{ "code": 400, "msg": "请求参数错误" }
```

| HTTP / code | 场景                                             | 设备处理                                                                     |
| ----------- | ------------------------------------------------ | ---------------------------------------------------------------------------- |
| 400         | 参数、类型、JSON 或 MAC 错误                     | 修正请求，不自动重复                                                         |
| 401         | 上线密码错误，或 start/stop 对应设备尚未上线登记 | 核对上线密码；先调用 loginMac，再以原实例 ID 重试通知；不携带 API KEY 请求头 |
| 404         | 接口路径或退下实例不存在                         | 核对路径、MAC 和实例 ID，不清理其他实例                                      |
| 409         | 登记冲突，例如尝试重新激活已结束实例             | 停止旧请求重试，核对设备当前实例                                             |
| 413 / 415   | 请求过大 / Content-Type 不支持                   | 修正请求                                                                     |
| 500         | 后端内部异常                                     | 保留原请求参数，退避重试                                                     |

### 6.2 重试与恢复规则

- 上线请求网络失败时可退避重试；成功后必须读取 `Authorization` 响应头。响应体成功但缺少 API KEY 时，不能视为已完成三方 LLM 配置。
- `start`、`stop` 网络失败或返回500时，可按1、2、4、8秒递增，最大间隔30秒退避重试。重试使用原 MAC、实例 ID 和本轮参数，不因通知失败重复创建百度实例。
- 新一轮开始后停止重试旧 `start`；旧 `stop` 如需重试，必须始终携带旧实例 ID，不得改成当前实例 ID。
- 仅 MQTT 断线、HTTP API KEY 仍有效时，恢复 MQTT 订阅、状态和心跳即可，无需因此重复调用三个 HTTP 接口。
- 后端若丢失登记状态，应让设备重新上线并登记仍在使用的实例。设备断电未发出退下通知时，后端结合 MQTT 离线状态处理记录，不能将离线判定当作云端实例已经释放的证据。
- MQTT 心跳和在线判定按《MQTT交互协议.md》执行；HTTP `start`、`stop` 不承担设备心跳。
